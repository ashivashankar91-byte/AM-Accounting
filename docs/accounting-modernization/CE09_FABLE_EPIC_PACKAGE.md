## EPIC OBJECTIVE
A dealership office runs its complete money-in / money-out operation inside AutoMate 2.0: vendors verified, invoices matched and approved, payments executed and voidable with rails; customers mastered with credit, billed, collected, NSF-handled; cash received at drawers, blind-closed, deposited, settled, reconciled to the bank — with every financial effect posting through the CE-07 engine, every controlled account tied out through CE-08 schedules, and the controller reading a truthful daily cash position.

## WORKSTREAM 3 — PAYMENT OPERATIONS & RAILS (S043B, S044, S045)

**S043B Payment Runs & Rails**. Proposal builder (due/discount date selection, vendor filters, cash-requirement preview) → approval of the *run* (SoD: proposer ≠ approver) → execution creating per-invoice payments atomically (all-or-none per payment, partial-run allowed with per-item results, nothing silent) → rail artifacts: check print file, positive-pay export, ACH/NACHA file via rail adapter (`PAYMENT_RAIL_NOT_CONFIGURED` truthful; file-generation-only is a valid mode — never fake transmission/acknowledgment). Check number issuance = gap-accounted sequence per bank account. AC: run idempotent (run id); per-invoice failure isolates (named), others proceed; positive-pay file totals = run totals; duplicate execution returns original results.
**S044 Trade-Payoff Fast Lane**. Expedited payment path for vehicle trade lien payoffs: payee = lienholder (payee-for-deal, not necessarily vendor-mastered — one-time payee with capture rules), per-diem-sensitive amount confirmation (amount + good-through date entered from payoff quote; system computes nothing actuarial), priority execution outside normal run cadence, links deal/stock reference for CE-12 consumption later [PUTR: deal linkage field only]. Posts payoff per matrix rows. AC: payoff payment references stock/deal id; good-through-date past ⇒ warning requiring re-confirmed amount; same guards as S043A.
**S045 Void/Stop/Reissue & Check Escheat**. Void before release (reverses payment journal via S218 linkage + restores open item), stop-payment request tracking against bank (adapter/manual acknowledgment, truthful), reissue = new payment linked to voided original (no duplicate relief — item restored then re-relieved once), escheat lifecycle: stale-date aging queue → due-diligence tracking → escheat transfer posting per matrix rows per state config [statutory timing = jurisdiction configuration table]. **Void after the payment cleared/reconciled ⇒ REFUSED — correction path is deposit/bank-side adjustment, never unwinding a reconciled item** [ACCOUNTING boundary; genuine rule: preserves S054A conservation]. AC: void restores item exactly once (race-tested); reissue cannot double-relieve; escheat queue ages from issue date; cleared-payment void refused with named result.
