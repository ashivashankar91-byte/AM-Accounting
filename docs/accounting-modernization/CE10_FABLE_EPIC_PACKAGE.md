# CE-10 — TAX · AUTHORITATIVE IMPLEMENTATION PACKAGE
**Canonical membership (frozen, registry-reconciled, 2):** S124 Certified Tax Engine Adapter (R2) · S125 Regulatory Fee Tables (R2). Direct-to-Claude-Code; no separate approval cycle. **Governing safety principle (approved): when an authoritative tax result is unavailable, BLOCK the transaction or route it to an explicit exception state. Never silently estimate tax.** This principle overrides convenience everywhere in this package.

## OWNERSHIP BOUNDARIES (stated once, enforced everywhere)
**Tax calculation** — owned by the external/configured tax engine behind the S124 adapter. CE-10 computes no tax law: no rates, no nexus, no taxability rules in code. **Tax mapping** — owned by Accounting: which accounts tax/fee amounts post to comes from the S023 governed matrix (new rows added blank; ACCOUNT_MAPPING_VALUES_PENDING; labeled test-tenant fixtures for certification; missing tenant mapping ⇒ deterministic rejection + S021 case). **Posting** — owned by CE-07: tax/fee lines travel inside the source transaction's SourceEventEnvelope; the engine posts one balanced journal; CE-10 never posts directly (zero direct GL writes, static check). **Consumption** — owned by CE-09/CE-11(/CE-12): those transactions *request* tax; CE-10 answers or blocks. Shared integration specifics carry `PENDING_UPSTREAM_TECHNICAL_RECONCILIATION` (PUTR) and do not block independent CE-10 build. **No invented tax content anywhere:** no default percentages, no seeded jurisdiction rules, no sample rates outside clearly-labeled test fixtures.

## S124 — CERTIFIED TAX ENGINE ADAPTER

### Objective & outcome
One adapter contract through which any certified tax engine answers "what tax applies to this transaction," with deterministic behavior when it can't — so dealership transactions (parts counter sales, service invoices, taxable AP self-assessment context, later deals) carry authoritative tax or stop, and the GL's tax liability provably reconciles to the engine's results.

### Adapter contract (vendor-agnostic; certification per vendor pending — see verdict)
**Request (TaxCalculationRequest):** tenant, legalEntity, store, documentType, documentId + line[] {lineId, itemClass/taxCategory code, amount, quantity, jurisdictionInputs (ship-from/ship-to/situs fields as engine requires), customer/vendor party ref, exemption ref if claimed, businessDate}, currency, correlationId, idempotencyKey (documentId+version). **Response (TaxCalculationResult):** per-line tax lines[] {jurisdiction id+level, tax type, rate AS RETURNED, taxable base, tax amount, engine result id}, document totals, engine version/content version, calculatedAt. **Result immutability:** stored verbatim as evidence; recalculation creates a new result linked to the document version — results are never edited. **Statuses:** CALCULATED · EXEMPT_APPLIED · ENGINE_UNAVAILABLE · ENGINE_REJECTED (with engine reason) · NOT_CONFIGURED. Only CALCULATED/EXEMPT_APPLIED allow the consuming transaction to proceed to posting with tax.
**Vendor implementations:** (1) `NullEngine` — always NOT_CONFIGURED (truthful default). (2) `TestFixtureEngine` — deterministic labeled fixtures for certification only; refuses to run outside test tenants. (3) Real vendor(s) — implement against this contract when selected; **no production vendor certification is claimed by this package**.

### Outage, retry, idempotency (the safety principle operationalized)
ENGINE_UNAVAILABLE ⇒ the consuming transaction is **blocked at submission** with a named state, or the user explicitly routes it to the **Tax Exception Queue** (transaction parked, nothing posts, nothing estimated). Retry: bounded automatic retries with backoff on transient failure, then exception state; every attempt logged. Idempotency: same request key returns the stored result — an engine retry can never double-calculate into a different posted amount; if the engine returns a different result for the same key, that is an integrity alert, not a silent overwrite. Recovery: exception-queue items re-request calculation on demand (or bulk after outage) and resume the source transaction's normal flow; all recovery audited (actor, before/after status). **At no point does any code path fabricate a rate, reuse a stale rate "temporarily," or post tax-less-than-requested silently.**

### Exemptions
Exemption certificates are **configuration + evidence, not tax law**: certificate registry per customer/party {jurisdiction scope, exemption type code AS DEFINED BY the engine/jurisdiction config, effective from/to, certificate document metadata, status}. The adapter passes the exemption reference; the **engine decides applicability** (EXEMPT_APPLIED comes back from the engine, not from local logic). Expired/absent certificate ⇒ request goes without exemption; UI shows why. Certificate lifecycle audited; expiring-certificate queue.

### Effective dating
Every configuration object (engine connection, jurisdiction registrations, exemption certs, mapping references) is effective-dated; calculation uses configuration effective at the transaction's businessDate; history is inquirable (below) and immutable. Backdated transactions calculate under the configuration effective on their date — never today's.

### Reconciliation: engine results ↔ GL
Persistent result store enables the two proofs: **(1) Transaction-level:** every posted journal's tax lines tie to a stored engine result (result id pinned on the envelope's tax lines — PUTR: field name on final envelope). Orphan checks both ways: posted tax without a result, and CALCULATED results whose transaction never posted (aging worklist). **(2) Period-level (close-period tax reconciliation):** for a period × entity × jurisdiction: Σ engine-result tax = Σ posted tax-line amounts = tax-liability GL account movement (accounts via matrix). Variance ⇒ loud report with drill to the discrepant documents; **an unreconciled tax variance is surfaced to the close process (CE-15 consumes; PUTR)** — CE-10 provides the report and the gate signal, not the close ceremony.

### Reporting
Jurisdiction liability report (period × entity × jurisdiction × tax type: taxable base, tax, posted, variance) — the remittance-preparation source; exception/outage report; exemption usage report. All render-verbatim from APIs; exports retained + audited. **Excluded: filing/remittance transmission** (compliance vendor / CE-17 scope).

### UI (unified shell; all standard states, permission-aware, 200% zoom, refresh-persistent; no separate shell; design-system components re-implemented in production React, never pasted HTML)
- **Tax Vendor / Adapter Status** `/accounting/tax/adapter` — persona: Controller/Admin. Connection status card (engine, engine version, content version, last successful call, NOT_CONFIGURED truthful banner), test-connection action (audited), effective-dated connection config history. States incl. ENGINE_UNAVAILABLE banner with queue-depth link.
- **Jurisdiction Administration** `/accounting/tax/jurisdictions` — registrations this tenant/entity holds (jurisdiction id from engine's reference data — browsable via adapter, never free-typed law), effective dates, registration numbers; table + drawer form; validation: overlap prevention per jurisdiction.
- **Exemption Configuration & Inquiry** `/accounting/tax/exemptions` — certificate registry table (party, scope, type, effective, status badges: ACTIVE/EXPIRING/EXPIRED), drawer with document metadata + audit tab; expiring queue tab; filters party/jurisdiction/status.
- **Calculation / Result Inquiry** `/accounting/tax/results` — searchable result store (document ref, date, entity, jurisdiction, status), result detail drawer: request snapshot, per-line jurisdiction breakdown AS RETURNED, engine/content versions, linked journal (drill to S217) or unposted-aging badge; immutable, no edit actions.
- **Exception & Outage Queue** `/accounting/tax/exceptions` — persona: Accountant. Parked transactions with reason (ENGINE_UNAVAILABLE / ENGINE_REJECTED detail / NOT_CONFIGURED), re-request action (single + bulk post-outage), disposition history; empty state: "No tax exceptions — engine healthy."
- **Tax Liability Reconciliation** `/accounting/tax/reconciliation` — period/entity selector via context bar; three-way tie table (engine Σ / posted Σ / GL movement) per jurisdiction with variance column and BALANCED badge or loud variance banner + drill; report-screen pattern; export.

Browser-test requirements per surface: happy render, empty, unauthorized (named permission), cross-tenant 404, one validation failure, one state-specific beat (adapter: NOT_CONFIGURED banner; exceptions: re-request success; reconciliation: injected variance shows loud).

### APIs / data / security
APIs: adapter internal (calculate/status/reference-data browse); config CRUD (connection, jurisdictions, exemptions) effective-dated, idempotent commands, optimistic concurrency; result query; exception queue + re-request; reconciliation query. DB (additive): tax_engine_config, jurisdiction_registrations, exemption_certificates, tax_results (+lines, immutable), tax_exceptions, all tenant+entity keyed, RLS pos/neg tested, non-superuser pattern. Permissions (manifest → S207): tax.config.view/manage (config manage = Controller-tier), tax.result.view, tax.exception.disposition, tax.reconciliation.view; config changes and exemption changes SoD-relevant (change vs approve = single-permission v1, audited — no genuine financial-rule gap: the engine, not the config author, computes tax). Audit: every config change (before/after), every calculation attempt + status, every exception disposition, every re-request, exports.

### S124 acceptance criteria
AC1 Given a configured (fixture) engine and a taxable request, Then a CALCULATED result stores verbatim with jurisdiction lines and the consuming transaction's envelope carries the result id; posted journal tax lines equal the result exactly. AC2 Given ENGINE_UNAVAILABLE, Then the transaction blocks or parks in the exception queue; nothing posts; no estimate exists anywhere; recovery re-request resumes and posts correctly. AC3 Given a duplicate calculation request (same key), Then the stored result returns; a divergent engine answer for the same key raises an integrity alert, never overwrites. AC4 Given an exemption certificate effective at businessDate, Then the request carries it and EXEMPT_APPLIED reflects the engine's decision; expired cert ⇒ request without exemption, visible reason. AC5 Given a backdated transaction, Then calculation uses configuration effective at that date (history-proof test). AC6 Period reconciliation on fixtures proves engine Σ = posted Σ = GL movement, and an injected orphan/variance shows loudly with drill. AC7 NOT_CONFIGURED tenant ⇒ every taxable path blocks/parks truthfully; nothing silently proceeds untaxed where tax was requested.

## S125 — REGULATORY FEE TABLES

### Objective & scope boundary
Configured, effective-dated regulatory fee tables (tire fees, battery fees, EPA/environmental, doc-fee-adjacent regulatory charges, state-specific vehicle fees) that consuming transactions (CE-09 counter sales, CE-11 RO/parts, later CE-12 deals) attach as fee lines posting through the engine per matrix rows. **Fee AMOUNTS/rules are jurisdiction-sourced configuration entered by authorized users — never shipped as code defaults; an empty table means the fee does not apply, truthfully.** Where a fee is percentage-based or tax-interacting (fee-on-fee, taxable fees), the *interaction* question is answered by the tax engine/config (S124), not local logic.

### Model & behavior
fee_tables {tenant, entity scope, jurisdiction ref, fee code, name, basis: FIXED_PER_UNIT | FIXED_PER_DOCUMENT | PERCENT_OF_BASE (base definition from configuration enum), amount/rate AS ENTERED, taxability flag (passed to S124), effective from/to, active} + per-fee applicability tags (itemClass/documentType codes) consumed by transactions to resolve applicable fees at businessDate. Resolution is deterministic; two overlapping active rows for the same fee code+scope+date ⇒ configuration validation error at save (never runtime ambiguity). Fee lines travel in the source envelope; accounts via matrix rows (blank; pending values); posting via CE-07. Effective-dated history; changes audited before/after.

### UI
- **Regulatory Fee Administration** `/accounting/tax/fees` — persona: Controller/Admin. Table (fee code, name, jurisdiction, basis, amount/rate, effective, status), filters jurisdiction/status/date, drawer form with overlap validation + basis-specific fields, history tab, deactivate (never delete once referenced — 409 with reference count). Empty state: "No regulatory fees configured — fees apply only when configured."
- **Fee Inquiry on transactions** — consuming-surface pattern (PUTR: rendered by CE-09/CE-11 screens): fee lines display code, basis, configured source table version.
Browser tests: overlap rejection; effective-date resolution across a boundary date; deactivate-with-references 409; unauthorized; empty-table truthfulness (transaction shows zero fees, no error).

### S125 acceptance criteria
AC1 Given a configured fee effective at businessDate matching a transaction's applicability tags, Then the fee line resolves deterministically with the configured amount/basis and posts per matrix rows within the source journal. AC2 Given overlapping candidate rows at save, Then validation rejects naming both rows. AC3 Given an empty/no-match table, Then no fee applies and nothing errors or estimates. AC4 Given a backdated transaction, Then the fee version effective at that date applies (history-proof). AC5 Given a percentage/taxable fee, Then base and taxability route through S124's request — no local tax math. AC6 A fee-table change never alters previously posted documents (immutability proof).
