00

Read Me and Status

Project purpose

Establish a single, implementation-ready UX foundation for the AutoMate Accounting module so that every General Ledger screen shares one shell, one component vocabulary and one set of financial-presentation rules. R0 proves the foundation on the highest-risk screen: Journal Entry.

Current application status

The Accounting module is functional but prototype-quality. Working backend behaviour exists for the Draft → Validate → Post → View → Reverse workflow. The front end presents it as unstyled form controls, inline text links and numbered plain-text steps.

No accounting logic is being changed in R0. This is a presentation, structure and state-coverage pass.

Evidence used

Reference A — Solera-family dealership shell

Used for visual language only: purple navigation rail, white work surfaces, blue primary actions, dark navy section headers, hairline borders, compact enterprise density, tabs / cards / data tables. Workflow, content and fields from that screen are not carried over.

Reference B — current AutoMate Accounting screens

Used as the source of truth for behaviour: existing Journal Entry workflow, field set, filter set, validation messaging and cross-screen links. Everything functional in the redesign traces back to something already present.

Design principles

The ledger is the interface

Lines, amounts and totals get the space. Chrome does not.

Backend is authoritative

The UI computes totals for usability, never for permission to post.

Context is always visible

Entity, store, department and fiscal period never leave the screen.

State is explicit

Draft, Validated, Posted and Reversed each look and behave differently.

Destructive work is deliberate

Post and Reverse are confirmed, attributed and audited.

Dense, not cramped

A full journal fits on one screen without scrolling the totals away.

Known assumptions

  1. Users are trained, frequent, desktop Accounting staff at a North American dealership group.
  2. A user may be scoped to more than one legal entity and store within one dealership group.
  3. Journal balancing, period status and posting eligibility are decided server-side.
  4. Posted journals are immutable; correction happens through reversal, not edit.
  5. Every workflow transition is auditable and attributable to a user and timestamp.
Assumptions are stated, not silently applied. Each one that affects behaviour has a matching entry in the decision register.

Financial presentation rules

These rules are non-negotiable across every Accounting screen.

Specimen only. Debits left column, credits right column, both right-aligned on a shared decimal grid; empty side renders an em dash, never a zero. Negative values are parenthesised and red, never minus-signed.
Monetary alignment. Right-aligned, tabular mono, two decimals always, thousands separated. Column width is fixed so decimals stack across every row and the totals footer.
Debit & credit. Two dedicated columns, never one signed column. A line carries a value in exactly one of them; the UI blocks entry in both.
Totals & variance. Totals footer is pinned to the bottom of the lines table and stays visible while lines scroll. Variance shows an absolute amount plus which side is short. Variance of zero is stated as In balance, not left blank.
Status colour. Draft amber · Validated blue · Posted green · Reversed slate. Status appears as a badge beside the page title and as a row treatment in any journal list.
Validation colour. Error red is reserved for backend-rejected states. Client-side hints (a field left empty, an unbalanced running total) use amber and never claim the journal has failed validation.
Focus. 2px #0B5CAB outline with 1px offset on every interactive element, including table cells in edit mode. Focus is never removed, only restyled.

Accessibility expectations

Contrast

WCAG 2.2 AA. Body text ≥ 4.5:1, uppercase labels ≥ 4.5:1, non-text UI boundaries ≥ 3:1. Status is never colour-only — every badge carries its word.

Keyboard

Whole journal completable without a mouse. Logical tab order down the line grid, Enter to commit a cell, Escape to cancel, no keyboard traps in the account lookup.

Screen reader

Lines table uses real table semantics with scoped headers. Totals footer is a live region. Validation banners announce assertively and receive focus.

Motion & zoom

No animation beyond 150ms state transitions; honours reduced-motion. Layout survives 200% browser zoom at 1280px with horizontal scroll on the lines table only.

04

Journal Entry

Current-screen assessment

1Workflow is plain text. Draft / Validate / Post / Reverse read as a numbered list rather than actionable controls, so the current state of the journal is never visible.
2No status object. Nothing on screen says whether this journal is a draft, validated, posted or reversed.
3Context is unlabelled input boxes. Entity, store, department and period sit in a row of bare fields with no grouping, units or open/closed indication.
4Cross-screen navigation is a sentence of links separated by middots, below the content, competing with the workflow itself.
5No visual hierarchy or work surface. Content floats on the page ground; the eye has no entry point and the page reads as an unstyled form.
6No table conventions. Money is not right-aligned or tabular, debit and credit are not visually paired, and totals are not pinned.
7Empty and error states are undefined. The screen renders the same regardless of whether data loaded, failed or is forbidden.
✓What is already right: the workflow itself, the field set, the filter set and the backend validation behaviour. All are preserved unchanged.

Why nothing is marked ready

Design and state coverage are complete for sections 04–09. No section can be marked READY_FOR_IMPLEMENTATION because API mapping and permission mapping are unresolved everywhere — endpoint names, permission keys, audit event names and error codes have not been supplied, and inventing them would violate the source-of-truth rule. Once the Story Contract and certified API behaviour are attached, the mappings can be filled in without changing a single screen.
