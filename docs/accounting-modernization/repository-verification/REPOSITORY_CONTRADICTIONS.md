# Repository Contradictions

Every item below is a direct, checkable conflict between an authoritative document's claim and what the repository actually contains — not a matter of interpretation.

## 1. CURRENT_RELEASE.md is stale and actively wrong

`docs/accounting-modernization/releases/CURRENT_RELEASE.md` carries the same `lastUpdated: 2026-07-24` date as `MODULE_STATE.json`, and its own header instructs: *"Do NOT edit this file directly. Update MODULE_STATE.json... To regenerate: `scripts/accounting-release-status.sh`."* Yet it:

- Names **R0-ACCOUNTING-SETUP** as the "Active package" and reports "Package completion: 8/8 (100%)," while `MODULE_STATE.json.activePackage` is **R0-JOURNAL-LIFECYCLE**, already itself `PACKAGE_COMPLETE_WITH_PENDING_INTEGRATIONS` (7/7).
- States explicitly: *"Journal posting (S013/S214) and reporting stories are out of scope for this package and await individual PO release."* MODULE_STATE.json shows S013, S214, S215, S216, S217, S218, S219 all implemented, tested, and `DONE_PENDING_INTEGRATION` as of 2026-07-24/25.
- Never mentions S013 or any of S214–S219 anywhere in the file.

This means the one document explicitly designed to be human-readable and authoritative ("Control file... Human-Readable Summary") is **at least one full package behind reality**, and its scope claim ("journal posting is out of scope") is false as of the same date it claims to be current. `MODULE_STATE.json`'s own `onStoryComplete` execution rule requires regenerating this file after every story close — that rule was not followed for the last 7 stories closed.

## 2. S200 and S207 claim full "DONE" with `usesStubs: false`, but use the same stub pattern as `usesStubs: true` stories

- S200 (`usesStubs: false`): `legal-entity-routes.ts` uses a local static `ROLE_PERMISSIONS` map, identical in kind to the stub used by S201/S203/S204 (all `usesStubs: true`). Its `/:id/audit` endpoint silently returns `[]` on any failure to reach a non-wired `audit-service`.
- S207 (`usesStubs: false`): the underlying `AuthzService.check()` engine is real, but per `AUTHORIZATION_AND_AUDIT_VERIFICATION.md`, it is not consumed by 19 of the other 21 stories, which each carry their own local stub instead. The story marked as the platform's single source of authorization truth is not actually functioning as one anywhere outside its own service.

`usesStubs: false` should mean "no known-temporary stand-in code remains in this story's delivered surface." Neither claim holds up against direct code inspection.

## 3. ADR-001 claims RLS was already delivered; it does not exist anywhere in the repository

ADR-001 §4: *"WI-UQ01-01 (the currently released work item) implements the RLS pattern for `legal_entities` and `tenant_outbox_events` as the reference implementation."* `DECISION_REGISTER.md` marks UQ-01 "RESOLVED → DEC-001 (RLS)." A repository-wide grep for `ROW LEVEL SECURITY`/`CREATE POLICY` returns **zero results**. See `TENANT_ISOLATION_VERIFICATION.md` for full detail. This is not a pending-integration item — the ADR describes it in the past tense as already shipped, and it isn't.

## 4. All 22 "done" stories' implementation is uncommitted; none of it has been pushed

`git log --oneline -- services/tenant-service services/auth-service services/coa-service` returns 2 commits, neither referencing any of the 22 stories. `origin/main` is byte-identical to local `HEAD`. Every application/domain/http/prisma-migration/test file implementing S200–S219 is either `?? ` (untracked) or ` M` (modified-uncommitted) in `git status`. See `REPOSITORY_IDENTITY.md` for the full breakdown. A "DONE"/"DONE_PENDING_INTEGRATION" status implicitly suggests reviewed, merge-ready work; none of this has been through any commit, review, or CI process at all.

## 5. Tenant-service has no audit mechanism for the 4 stories MODULE_STATE says need an "AuditPort stub swap"

MODULE_STATE.json's `R0-ORG-FOUNDATION.carryForwardIntegrations`: *"S007 audit integration — swap the AuditPort stub (audit_outbox / *_outbox_events tables) for the real S007 audit consumer across S203, S204, S205, S206 (and S201)."* `services/tenant-service/prisma/schema.prisma` (covering S200/S201/S203/S204) contains **no `AuditOutboxEvent`/`audit_outbox` model at all** — there is no stub to swap for these four stories; there is nothing.

## 6. Missing completion documentation for 2 of 22 "done" stories

MODULE_STATE.json requires `docs/accounting-modernization/audit-results/{STORY}-COMPLETION.md` on every story close (`onStoryComplete` rule). `S201-COMPLETION.md` and `S203-COMPLETION.md` do not exist in `audit-results/`, despite both stories being marked `DONE`/`DONE_PENDING_INTEGRATION`.

## 7. Wave 1.2 "Repository Correction" validator does not exist

The verification brief that produced this audit assumes a `Wave_1_2_Repository_Correction.zip` / `validate_wave_1_2_correction.py` exist. Neither does. Only an unrelated `Wave_1_2_Decision_Package.zip` (a Payroll build-vs-buy decision package) shares the "Wave 1.2" name. See `VALIDATION_PACKAGE_REPRODUCTION.md`.

## 8. All three core services fail TypeScript compilation despite 100% unit-test pass rates

`tsc --noEmit` fails with real, non-cosmetic errors in `tenant-service` (2), `auth-service` (2), and `coa-service` (9) — see `TEST_EXECUTION_REPORT.md`. The coa-service failures are specifically in the stub-authz route files. A codebase claiming CLAUDE.md's "Zero Tolerance... 100% correct and production-ready" standard should not fail its own compiler.
