# R1 Integration — Test-Data and Certification Debt Register

This register tracks integration-level test-data and certification gaps
discovered during R1 Controlled Integration. Entries here are disclosed
debt, not resolved gaps — they must not be silently assigned to any single
story's production scope, and must not be described as fixed until an
explicit resolution is recorded against the relevant entry.

---

## DEBT-INT-001 — Fresh-stack historical GL certification dataset

**Opened**: 2026-07-29 (R1 Controlled Integration, Step 1C — S008 isolated
integrated-runtime certification)

**Description**: `golden-path.spec.ts`'s main 16-step journey asserts against
Trial Balance/Balance Sheet/Income Statement data for legal entity `01`,
`asOf 2026-02`, that was "already-certified, pre-seeded evidence data...
from the S014/S222/S227 backend certification sessions" — accumulated
incrementally, by hand, across many long-lived-stack sessions. No
deterministic seed script exists in the repository to reproduce this
dataset on a fresh, empty database. This is a pre-existing gap
(`PHASE4_FRESH_STACK_PLAYWRIGHT_EXCEPTION.md`), re-confirmed live during the
S008 Step 1C isolated-runtime run (Golden R0 Playwright 13/14; the one
failure is this gap, observed as a correct, non-error empty Trial Balance
state).

**Required outcome**:
- Deterministic posted GL history, generated by a repeatable seed process
  (not hand-accumulated across sessions).
- Trial Balance populated.
- Balance Sheet populated.
- Income Statement populated.
- Repeatable from an empty database.
- No dependency on any long-lived database.

**Blocks**:
- Combined demonstration certification.
- Final Wave-0 reporting certification.

**Does not block**:
- S003 selective integration.

## DEBT-INT-003 — Repeat-safe S008 Playwright fiscal-period fixture

**Opened**: 2026-07-29 (R1 Controlled Integration, Step 1C)

**Description**: `tests/e2e/fiscal-period-close.spec.ts` deliberately
operates on a dedicated fiscal year (2099) so it never collides with other
suites in a single run — but this also means a second run against the same,
already-mutated database legitimately fails at its first assertion, because
the spec assumes the year starts at `OPEN` and by the second run period
2099-01 is already `LOCKED` (terminal, no unlock — the exact guarantee S008
exists to enforce). This surfaced in the full-E2E run as an apparent S008
failure; it is the terminal-state protection working exactly as designed,
not a regression, but it means the suite is not currently repeat-safe
end-to-end.

**Required outcome**:
- Each run receives a new deterministic fiscal year/period, or the suite
  resets only its own test data safely between runs.
- Re-running the suite must not encounter an already-`LOCKED` terminal
  period from a prior run.

**Blocks**:
- Repeatable full-suite certification.

**Does not block**:
- First S003 integration pass.
