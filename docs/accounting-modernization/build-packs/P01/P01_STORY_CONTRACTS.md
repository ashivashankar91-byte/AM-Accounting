## S008 — Fiscal Period Close, Reopen and Lock Control
**Feature CF-06.1 Period Governance · Epic CE-06 · Persona: Controller**
**Contract status for this story: IMPLEMENTED_CONTRACT_V1 (supersedes the PROPOSED_CONTRACT_V1 text below for S008 only — every other story in this pack remains PROPOSED_CONTRACT_V1). This section describes the actual, already-migrated, already-PO-approved production behavior on `r1-s008-period-close-control`, not a proposal. Reconciled against the repository and confirmed by Product Owner decision "PRODUCT DECISION — S008 CONTRACT RECONCILIATION" (2026-07-28); see `P01_REPOSITORY_VERIFICATION_RECONCILIATION.md` §2 for the prior conflict this resolves.**

**Story.** As a Controller, I need to soft-close, hard-close, reopen and lock fiscal periods with enforced posting control, so the books for a month stop moving when I say they stop moving — and can only move again through a deliberate, audited ceremony.

**Problem.** Legacy month-end depends on discipline, not enforcement ("Close Out Month" + "FAQ Problems Setting Month End Close Flag" source docs): a flag that people work around. R0 delivers only FUTURE→OPEN (S209). Without close states, R1 governance is fiction.

**State machine (extends S209; S209 transitions untouched):**
`FUTURE → OPEN → SOFT_CLOSED → HARD_CLOSED → LOCKED`. `LOCKED` is **terminal** — no unlock operation exists at any layer: no normal API, no break-glass endpoint, no supported manual database correction. The `enforce_period_transition()` DB trigger rejects any transition attempted out of `LOCKED` (SQLSTATE `AMPR5`), independent of and in addition to the application gate, so this holds even against a hypothetical direct-SQL bypass. There is **no** `HARD_CLOSED → SOFT_CLOSED` "unlock" transition of any kind — that path does not exist in the allowlist. Reopening is instead a two-tier model, both landing on `OPEN`:
- `SOFT_CLOSED → OPEN` — the ordinary **reopen**, gated by `fiscal.period.reopen` (CONTROLLER + ADMIN).
- `HARD_CLOSED → OPEN` — the elevated **reopen-hard-closed**, gated by the distinct, higher `fiscal.period.reopen_hard_closed` permission (ADMIN only), and requiring an explicit second confirmation step (see Alternate flow below).

No transition skips a state; the full legal allowlist (mirrored identically by the DB trigger and by `domain/period-status.ts canTransition()`) is exactly: `FUTURE→OPEN`, `OPEN→SOFT_CLOSED`, `SOFT_CLOSED→OPEN`, `SOFT_CLOSED→HARD_CLOSED`, `HARD_CLOSED→OPEN`, `HARD_CLOSED→LOCKED`. The year-close/13th-month interplay this section previously flagged is moot: `LOCKED` already has zero recovery by design, so there is no "non-unlockable" edge case to separately resolve.

**Business rules.**
- BR008-1 OPEN: all postings permitted (unchanged).
- BR008-2 SOFT_CLOSED: postings are rejected **except** for an authorized manual adjusting entry. The allowlist is **per-journal attestation, not source-code or role alone**: a journal may post into a `SOFT_CLOSED` period only when `isAdjusting=true` **and** a matching row exists in `adjusting_entry_attestation` for that draft (written by `DraftService` at the moment a preparer holding `fiscal.je.mark_adjusting` makes the call). Automated/system-source postings are always blocked in `SOFT_CLOSED` — the DB trigger does not special-case caller class, so no source can bypass the attestation requirement. Enforced identically at the application layer (`journal-posting.ts` BR013-2, in the shared evaluator also used by validate) and at the database layer (`enforce_period_postable()`, SQLSTATE `AMPR1`/`AMPR6`) — the two are required to never diverge and are checked against each other in the live-code proof.
- BR008-3 HARD_CLOSED: no postings, no exceptions, enforced at the database. `posting-service.ts` is the application gate; `enforce_period_postable()` (a `BEFORE INSERT ON journal_entry` trigger) is the backstop. Single-write-door analysis confirms `posting-service.ts` is the only `tx.journalEntry.create` call site in the codebase (both manual post and reversal funnel through it), so the trigger covers every posting path, including a hypothetical direct-SQL insert.
- BR008-4 Reopen requires a non-empty, non-whitespace reason (validated as `1–500` chars at the route schema, not the originally proposed 10-char minimum) and emits a distinct audit event on `docType: 'fiscal_period'`: `REOPEN` for the `SOFT_CLOSED→OPEN` path, `PERIOD_REOPENED_FROM_HARD_CLOSE` for the `HARD_CLOSED→OPEN` path. Reopening does not alter any posted journal — no reopen code path touches `journal_entry` rows.
- BR008-5 Hard-close prerequisite: period must be `SOFT_CLOSED`, and no open (`DRAFT`/`VALIDATED`) journal draft dated inside the period may exist. Resolved to **block, not auto-roll**: a blocking draft returns `422 HARD_CLOSE_BLOCKED_BY_DRAFTS` with a named worklist (`draftId`, `entryDate`, `amount` — the sum of the draft's debit legs, `preparer`), one entry per blocker; `VOIDED` and `POSTED_LINKED` drafts never block. No transition occurs while any blocker remains.
- BR008-6 Sequential close (a period cannot hard-close while an earlier `OPEN`/`SOFT_CLOSED` period exists in the same fiscal year): **not implemented in S008 v1** — no code path checks this, and `hardClose()` does not consult sibling periods. This remains a genuine, disclosed gap (previously `SME_VALIDATION_REQUIRED`), not silently resolved; it is open for a future story if Product wants it enforced.
- BR008-7 `max_open_periods` config (S223) continues to govern how many `OPEN` periods may exist via the pre-existing `open()` path; unaffected by this story's close/reopen/lock additions.

**Primary flow.** Controller opens Period Control → selects 2026-08 (`OPEN`) → "Soft close…" with a mandatory reason → `SOFT_CLOSED`, board + timeline update, audit event (`SOFT_CLOSE`). Later: "Hard close…" with a mandatory reason → prerequisite check (open in-period drafts = 0, else `422` with the named worklist) → `HARD_CLOSED` (audit event `HARD_CLOSE`). Optionally, later still: "Lock…" with a mandatory reason → irreversible-action confirmation (`confirm=true` required on a second submit, matching the destructive-ceremony pattern) → `LOCKED`, terminal (audit event `LOCK`).
**Alternate.** Reopen a `SOFT_CLOSED` period with a reason (`fiscal.period.reopen`, CONTROLLER/ADMIN) → back to `OPEN`. Reopen a `HARD_CLOSED` period via the distinct **reopen-hard-closed** action (`fiscal.period.reopen_hard_closed`, ADMIN only): first submit (reason, no `confirm`) returns `requiresConfirmation: true` with a high-severity warning message and makes no change; re-submit with `confirm=true` executes the transition and emits `PERIOD_REOPENED_FROM_HARD_CLOSE`. This is a **single-permission, two-step-confirm** ceremony, not a dual-person/second-approver ceremony — PO decision: dual approval is not required in S008 v1. There is no unlock ceremony of any kind for `LOCKED`.
**Exceptions.** Posting into `SOFT_CLOSED` without a valid attestation → app-layer `422 POSTING_REJECTED` (rule `BR013-2`) and, if the app gate were ever bypassed, DB rejection (`AMPR1`/`AMPR6`); posting into `HARD_CLOSED` or `LOCKED` → same app-layer rejection, DB backstop `AMPR1`; hard-close attempt with open drafts → `422 HARD_CLOSE_BLOCKED_BY_DRAFTS` with the draft worklist, no transition; unauthorized → `403`; cross-tenant → `404 PERIOD_NOT_FOUND` (tenant mismatch resolves to not-found, never a distinct cross-tenant error); missing/blank reason → `400 PERIOD_REASON_REQUIRED`; irreversible action (lock, reopen-hard-closed) without `confirm=true` → `422 CONFIRMATION_REQUIRED`, no transition; concurrent transition race → resolved by a CAS-guarded `updateMany` (`WHERE id = ? AND status = <expected-from>`); the loser gets `422 INVALID_TRANSITION` reflecting the now-current status, never a distinct `409` — there is no optimistic-lock version field or `409` status in this implementation.

**Data.** `FiscalPeriod` (existing, S208/S209) gains `closed_by`/`closed_at` (set on every transition into `SOFT_CLOSED` or `HARD_CLOSED`, representing only the most recent close-family transition; cleared to `NULL` on any reopen) and `locked_by`/`locked_at` (set exactly once, on `HARD_CLOSED→LOCKED`; never cleared, since `LOCKED` is terminal). All four are written only by the `enforce_period_transition()` trigger, never directly by application code. A new append-only ledger table, singular `fiscal_period_transition` (not `fiscal_period_transitions`) — `{id, tenant_id, entity_id, period_id, from_status, to_status, actor, occurred_at}` — is written by the trigger via a `SECURITY DEFINER` function (`record_period_transition`), executed as a narrow `amacc_period_ledger_writer` role with no other privileges on the table; the application role (`amacc_app`) has its own INSERT/UPDATE/DELETE revoked on this table, so it cannot write to it directly even if it tried. **This table does not carry a `reason` column** — the trigger that writes it is never handed one. The reason is carried instead in the S007 audit outbox (`docType: 'fiscal_period'`, `after.reason`), written by the application in the same transaction; the Period Status Timeline UI (P01-SCR-01) sources its "last transition" summary from the audit outbox for this reason, not from `fiscal_period_transition`. A second new table, `adjusting_entry_attestation` — `{id, tenant_id, draft_id (unique), attested_by, reason, correction_ref, created_at}` — records the `fiscal.je.mark_adjusting` decision per draft, read by `enforce_period_postable()` at posting time. Both new tables carry the same tenant-isolation RLS pattern as the rest of the schema (`FORCE ROW LEVEL SECURITY`, tenant-scoped `SELECT` policy, no permissive write policy for `amacc_app`/`PUBLIC`). Owning service/schema: `coa-service` (`services/coa-service/prisma/schema.prisma`).

**API (IMPLEMENTED_CONTRACT_V1 — five distinct verbs, not one generic `/transitions` endpoint).** All routes are registered under `/periods` in `coa-service` and reachable through the gateway at `/api/v1/fiscal/periods/*` (`services/api-gateway/src/index.ts` proxies `/api/v1/fiscal` → `coa-service`, unchanged from S209).
- `GET /periods?entity=<entityId>` → the status board: every period for the entity (all fiscal years, ordered ascending) with `status`, `adjustmentsOnly`, `openedBy`/`openedAt`, `closedBy`/`closedAt`, `lockedBy`/`lockedAt`, `openDrafts` (count of in-period `DRAFT`/`VALIDATED` journals — the hard-close worklist preview), and `lastTransition: {fromStatus, toStatus, reason, actor, at}` sourced from the audit outbox. Not year-filterable (`?year=` from the original proposal does not exist) — scoped by `entity` only.
- `GET /periods/{id}/eligibility` → postability + reason (existing S209 endpoint, extended for the full status set).
- `POST /periods/{id}/open {confirm?}` → `FUTURE→OPEN` (pre-existing S209 route, now additionally gated by the same DB trigger).
- `POST /periods/{id}/soft-close {reason}` → `OPEN→SOFT_CLOSED`.
- `POST /periods/{id}/hard-close {reason}` → `SOFT_CLOSED→HARD_CLOSED`; `422 HARD_CLOSE_BLOCKED_BY_DRAFTS` with `blockingDrafts[]` if any block.
- `POST /periods/{id}/reopen {reason}` → `SOFT_CLOSED→OPEN` only; `422 INVALID_TRANSITION` if the period is `HARD_CLOSED` (directs the caller to reopen-hard-closed).
- `POST /periods/{id}/reopen-hard-closed {reason, confirm?}` → `HARD_CLOSED→OPEN`; two-step confirm as described above.
- `POST /periods/{id}/lock {reason, confirm?}` → `HARD_CLOSED→LOCKED`; two-step confirm; terminal.

Every route requires `x-tenant-id` (`400` if missing) and derives `actor` **only** from the verified JWT subject (`request.user.sub`), never from the request body, on all six write routes including the pre-existing `open()`. Idempotency is CAS-based, not client-token-based: retrying an identical transition after it already succeeded (period already in the target status) is a no-op success with no new transition/audit row; there is no idempotency-key request field.

**Authorization.** Actual catalog keys (`services/auth-service/prisma/migrations/20260728050000_extend_authz_catalog_s008_period_close`): `fiscal.period.view` (read), `fiscal.period.open` (pre-existing), `fiscal.period.soft_close`, `fiscal.period.hard_close`, `fiscal.period.reopen` — all four CONTROLLER + ADMIN — and the two elevated, ADMIN-only keys `fiscal.period.reopen_hard_closed` and `fiscal.period.lock` (the two-tier reopen model's higher tier). A related but distinct permission, `fiscal.je.mark_adjusting` (ADMIN + CONTROLLER + ACCOUNTANT), governs who may attest a draft as an adjusting entry for the `SOFT_CLOSED` posting exception — it is not itself a period-transition permission. Denied action buttons render disabled with permission tooltip (Foundation V1 pattern, frontend work item).

**Audit.** S007 audit outbox events on `docType: 'fiscal_period'`: `OPEN` (pre-existing), `SOFT_CLOSE`, `HARD_CLOSE`, `REOPEN`, `PERIOD_REOPENED_FROM_HARD_CLOSE`, `LOCK` — each with `before: {status}`, `after: {status, reason}` (reason present on every action except `OPEN`), `actor`, `tenantId`, `docId` (the period id), timestamp. The original contract's `fiscal.period.soft_closed|hard_closed|reopened|unlocked` event-name convention is superseded by these actual action strings; there is no `unlocked` event because no unlock capability exists.

**Acceptance criteria (corrected against implementation).**
- AC008-1 Given `OPEN` 2026-08 When soft-closed Then a non-adjusting posting rejects (`BR013-2`, both app and DB layers) and a properly attested adjusting entry succeeds.
- AC008-2 Given `SOFT_CLOSED` When hard-closed with zero blocking drafts Then any subsequent posting rejects and a direct-DB insert attempt fails the `enforce_period_postable()` backstop.
- AC008-3 Given `SOFT_CLOSED` When reopened with a reason Then postings resume and the audit outbox's `REOPEN` event carries the reason verbatim.
- AC008-4 Given open (`DRAFT`/`VALIDATED`) drafts dated in-period When hard-close attempted Then `422 HARD_CLOSE_BLOCKED_BY_DRAFTS` lists each draft (`draftId`, `entryDate`, `amount`, `preparer`) and no transition occurs.
- AC008-5 (openEarlierPeriods / BR008-6): **not certified — feature not built.** No test can pass for this AC because the underlying sequential-close check does not exist in this branch. Left open pending a Product decision on whether to build it.
- NEG: reopening never mutates posted journals (assert journal hashes/content unchanged) — holds structurally, since no reopen code path references `journal_entry`.

**DoR:** state-machine/permission/unlock questions are resolved (this section) per PO decision 2026-07-28; BR008-6 remains an open SME/Product decision, not resolved, and is out of scope for S008 v1 certification. **DoD:** vertical slice implemented and technically certified as of 2026-07-28 (concurrency/idempotency suite, RLS-negative suite, live-code PostingService proof, route-level authz-guard coverage, live-gateway confirmation, frontend, Playwright — all complete; PO checkpoint accepted, commits `ce35c3f`/`762e2b4`). ## S009 — Statement Metadata and COA Governance
**Feature CF-06.4 · Epic CE-06 · Persona: Controller**

**Story.** As a Controller, I need every account to carry statement classification and line metadata under governed edit control, so the Balance Sheet and Income Statement can group COST_OF_SALES and DISTRIBUTION correctly (lifting the Golden R0 limitation) and COA changes stop being casual.

**Business rules.**
- BR009-1 Statement metadata per account: `classification` (extends the certified enum — current enum values `API_CONFIRMATION_REQUIRED`) + `statementLine` (code from a tenant-scoped Statement Line registry: id, code, name, statement BS|IS, section, sort). Seed line registry: minimal internal BS/IS line set (proposed) — NADA/OEM line sets are R5 → `SME_VALIDATION_REQUIRED: minimal internal line list`.
- BR009-2 Statements consume metadata: with S009 live, 08/09 group COST_OF_SALES under a Gross Profit presentation and DISTRIBUTION under its section; the limitation banner retires. Exact IS presentation (Gross Profit subtotal placement) → `SME_VALIDATION_REQUIRED`.
- BR009-3 Governance: statement-metadata and account-status edits require `coa.governance.edit` (distinct from `coa.account.manage`); every change requires a reason; accounts with posted activity cannot change classification without an effective-period rule → `DECISION_REQUIRED: reclassification of accounts with history (proposed: allowed prospectively from an effective period, never retroactive restatement in R1)`.
- BR009-4 Unmapped guard: an account may exist without a statementLine (falls to its classification's default section) but never without a classification (existing invariant — `TECHNICAL_VERIFICATION_REQUIRED`).
- BR009-5 Bulk mapping: multi-select accounts → assign line (governed, one audit event per account + one batch event).

**Flows.** Primary: Controller opens COA Governance → filters unmapped/limitation-affected accounts (the exact accounts today's banner names) → assigns classification/line with reason → statements preview panel shows the resulting grouping (read-only render of 08/09 section for affected accounts) → save. **Data.** `statement_lines` (new, tenant-scoped) + `gl_accounts.statement_line_id` + `gl_accounts.classification` (existing — extension `TECHNICAL_VERIFICATION_REQUIRED`) + `coa_change_log` reasons (or reuse S007 payloads — proposed: S007 is the log, no parallel table). Ownership: gl/coa service.

**API.** `GET/POST/PATCH /coa/statement-lines`; `PATCH /coa/accounts/{id}/statement-metadata {classification?, statementLineId?, reason, effectivePeriod?}`; `POST /coa/accounts/statement-metadata:bulk`. Statements (S227 endpoints) gain grouped sections — response shape change is versioned (`eventVersion`/API version bump) → `API_CONFIRMATION_REQUIRED`.

**Authorization.** `coa.governance.edit`, `coa.statementline.manage`, read `coa.account.view`.
**Audit.** `coa.statement_metadata.changed` (before/after + reason + effectivePeriod), `coa.statement_line.created/updated/deleted`, batch event with account list.

**AC.** AC009-1 Given a COST_OF_SALES account mapped When the IS renders Then it groups under the approved section and the limitation banner does not show for it. AC009-2 Given an account with posted history When classification change attempted without effective period Then 422 rule-referenced. AC009-3 Given a line referenced by accounts When delete attempted Then 409 with reference count. AC009-4 Given bulk assignment of N accounts Then N audit events + 1 batch event, all with the shared reason. NEG: no metadata change ever alters posted journal lines or historical statement snapshots.

**DoR:** enum + reclassification decision + minimal line list SME-confirmed; 08/09 consumption contract agreed. **DoD:** slice + statements re-render proof + retired-banner Playwright assertion.

## S032 — Recurring Journal Templates and Generation
**Feature CF-06.2 · Epic CE-06 · Persona: Accountant / Controller**

**Story.** As an Accountant, I need recurring and auto-reversing journal templates generated on demand per period, so standard entries (rent, depreciation splits, accrual patterns from the legacy "Standard Journal Entries" and "Journal Posting Template" guides — ACC evidence cluster) stop being retyped and auto-reverse without memory.

**Hard scope rules (per pack instruction).** No S031 approval routing — generated journals follow the tenant's existing posting mode exactly as a hand-typed draft would. No schedule (S026–S029) behavior invented — template lines carry account + dimensions only; schedule-key fields appear only if the certified line schema already carries them (`TECHNICAL_VERIFICATION_REQUIRED`), and their semantics are untouched. Generation and any posting **reuse the certified S214 draft path and S013 gate** once technically verified — the generator is a client of the journal lifecycle, never a second posting path.

**Business rules.** BR032-1 Template: `{code, name, description, sourceCode (manual source — DECISION_REQUIRED: dedicated RT source vs GJ; proposed dedicated RT in S212 registry), lines[{account, dept?, store?, memo, dr|cr amount}], balanced required at save, active flag, autoReverse bool, schedule {frequency: EVERY_PERIOD | SELECTED_PERIODS[], generateOnDay? — proposed: manual/period-checklist trigger in R1, no cron → DECISION_REQUIRED}}`. BR032-2 Amounts fixed in R1; formula/percent amounts are a recorded non-goal → `DECISION_REQUIRED (proposed: defer)`. BR032-3 Generation for period P: creates **DRAFT** journals via the S214 path, one per template, dated per template rule (proposed: period-end date → `SME_VALIDATION_REQUIRED`), tagged `generatedFromTemplate` + generation batch id; posting is the human's act under existing permissions/mode (UQ-06 posting-mode interim governs — direct post default). BR032-4 Idempotency: generating twice for the same template+period returns the existing draft/journal, never a duplicate (batch-keyed). BR032-5 Auto-reverse: when a template is autoReverse and its generated journal posts in P, a reversing DRAFT dated first day of P+1 is created (S218 linkage semantics: `reversal_of`) — created at post time or at P+1 open → `DECISION_REQUIRED (proposed: immediately at post, dated P+1; posting it remains human)`.
